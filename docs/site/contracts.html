Contracts

Each algorithm has a contract: a short list of conditions it must satisfy. Some conditions are inputs it requires, and some are outputs it promises. The conditions are written down, checked by a solver where they are linear, and checked at run time where they are not.

What a contract says

Take KMeans. Its contract requires at least one row, k ≥ 1, and k ≤ rows. It promises that the inertia never increases from one iteration to the next, that once the assignments stop changing the fit has converged, and that every centre lies inside the convex hull of the data.

  • requires is a precondition. A caller that breaks it gets an error, not a result.
  • ensures is a postcondition. The implementation must make it true for every valid input.

The contract files are in docs/contracts/, one per algorithm, and the full reference is in docs/contracts/README.md.

How each clause is checked

CheckWhat it doesFails CI?
SolverA linear clause is checked by the QF_LRA solver from tpt-solver. A PROVEN result is accepted only after its certificate is checked.No, when proven. A DISPROVED or INCONCLUSIVE result does.
RuntimeA clause outside linear arithmetic, such as a product of variables, is enforced by a runtime assertion in the Rust source, and by property tests.Only the linkage: every clause needs a matching check.
LinkageEvery clause must name a runtime check in the source, so a contract cannot drift from the code.Yes.

Reading the verifier output

VerdictMeaning
assumedA requires clause. It is a hypothesis, and it is not checked.
PROVENThe solver showed the clause follows from the linear preconditions.
DISPROVEDA counterexample exists. The counterexample is printed. This fails CI.
UNVERIFIEDNot linear, so it is left to the runtime checks and the property tests. It fails CI only with --fail-on-unverified.
INCONCLUSIVEThe solver could not decide, or its answer could not be confirmed. This fails CI.

Run it

From the repository root:

cargo run --manifest-path tools/tptc-verify/Cargo.toml -- docs/contracts

Exit code 0 means no clause failed. CI runs this on every push, and the verifier's own tests include deliberately false contracts that must be rejected.

What contracts do not promise

A contract is a check on the algorithm, not a proof that it is correct in every sense. A proven clause is a fact about the linear part of the specification. Runtime checks catch violations on the inputs that actually run, and parity tests show the numbers agree with scikit-learn on the fixtures. Neither one covers every input.
